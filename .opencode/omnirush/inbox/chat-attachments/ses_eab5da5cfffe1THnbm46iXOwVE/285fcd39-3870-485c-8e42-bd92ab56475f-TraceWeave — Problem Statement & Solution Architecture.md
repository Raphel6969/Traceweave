# TraceWeave — Problem Statement & Solution Architecture

*Evidence-backed incident reconstruction. Facts, inferences, and unknowns — never blurred together.*

## 1. Problem Statement

### 1.1 Context

When an account is compromised, the evidence is scattered across systems that were never designed to agree with each other: an identity provider logs the login, the application logs the API-token creation and export, the network layer logs a large outbound transfer. Each source uses its own timestamp format, timezone, identifier scheme (user ID vs email vs session ID vs IP), and level of detail.

Incident responders must turn this into a **defensible sequence**: one they can put in a report, hand to legal, or defend to an auditor.

### 1.2 The Problem

Existing forensic tooling (Plaso/log2timeline, Timesketch, SIEM search) is excellent at *collecting and sorting* events into a super-timeline. It is much weaker at three things that actually decide whether a conclusion survives scrutiny:

1. **Claim provenance.** A conclusion such as "the attacker created a token and exfiltrated data" is rarely traceable, claim by claim, to the exact raw records that support it.
2. **Epistemic honesty.** Tools show *what happened* but rarely separate what was **observed** from what was **inferred** from what is **unknown**. Analysts do that in their heads, inconsistently, and under pressure.
3. **Contradictions and gaps.** Clock skew, missing audit records, and conflicting identities are silently flattened into a clean-looking timeline, which creates false confidence.

> **Problem statement:** *Design and build a deterministic incident reconstruction engine that ingests heterogeneous security logs, correlates events across sources, and produces a timeline in which every claim is classified as Observed, Inferred, or Unknown, is linked to exact source records, and is accompanied by an explicit confidence rationale, detected contradictions, and missing evidence.*

### 1.3 Objectives

- Normalize multi-source logs into a canonical event model without losing the raw record.
- Correlate events using shared identifiers and temporal constraints, via transparent rules (no black box).
- Represent the result as an evidence graph of observed events and *candidate* causal relationships.
- Attach provenance to every node, edge, and sentence of the report.
- Detect and surface contradictions (clock skew, identity conflicts, impossible ordering) and evidence gaps (what *should* exist but doesn't).
- Export a reproducible report (JSON + HTML) and an interactive investigation UI.

### 1.4 Target Users

| User | Need |
| --- | --- |
| Incident responder (SOC L2/L3) | Fast, trustworthy reconstruction across sources |
| DFIR consultant | Defensible report for a client or court |
| Compliance / audit lead | Proof of what is and isn't known about an incident |
| Engineering manager | Plain-language summary with no overclaiming |

### 1.5 Scope and Non-Goals

**In scope (MVP):** three log formats, one synthetic multi-stage incident, rule-based correlation, evidence graph, provenance layer, contradiction and gap detection, JSON/HTML report, test suite.

**Non-goals:** disk/memory forensics (Plaso's territory), real-time detection, automated remediation, LLM-generated narratives, replacing a SIEM.

### 1.6 Success Criteria

- Every statement in the report resolves to ≥1 raw source record (100% provenance coverage, enforced by test).
- The engine never labels a causal link as *Observed* unless a source record directly states it.
- Injected contradictions and gaps are detected in the synthetic cases (target: all of them).
- Same input yields byte-identical output (determinism).
- A judge can click any claim and see the raw log line within two interactions.

### 1.7 Differentiator (say this in the pitch)

*Plaso builds the timeline. TraceWeave tells you how much of that timeline you can defend.* The product is not the timeline; it is **provenance plus explicit uncertainty**.

## 2. The Core Idea: the Epistemic Model

Every output object carries exactly one of three states:

| State | Meaning | Example | Visual |
| --- | --- | --- | --- |
| **Observed** | A source record directly states it | "Login succeeded for user\_17 from 203.0.113.42 at 10:02:11" | Solid line, filled node |
| **Inferred** | Derived by a named rule from observed facts; not directly stated | "Token creation is plausibly linked to the login (same account, 53s later)" | Dashed line, outlined node |
| **Unknown** | Evidence that would be expected is absent or unavailable | "No record shows who used the token or what data was read" | Hatched node |

Rules the engine must obey:

- Inferred claims must cite the **rule ID** and the **observed facts** they were derived from.
- Unknowns are first-class outputs, generated by explicit *expectation rules* ("a token creation should be followed by a token-use audit record").
- Confidence is a **decomposed score** with named factors, never a single opaque number.

## 3. Solution Architecture

### 3.1 Layered Overview

```
┌──────────────────────────────────────────────────────────────┐
│ L7  Presentation   Next.js UI · GSAP · Graph + Timeline       │
├──────────────────────────────────────────────────────────────┤
│ L6  API            FastAPI · REST + SSE (analysis progress)   │
├──────────────────────────────────────────────────────────────┤
│ L5  Reporting      JSON · HTML · (optional) PDF · LLM explainer│
├──────────────────────────────────────────────────────────────┤
│ L4  Reasoning      Correlation rules · Confidence · Contradiction│
│                    detector · Gap (expectation) engine        │
├──────────────────────────────────────────────────────────────┤
│ L3  Evidence Graph  Nodes: events/entities · Edges: observed/  │
│                    inferred · Claims with provenance           │
├──────────────────────────────────────────────────────────────┤
│ L2  Normalization  Parsers → canonical events · Entity resolve │
├──────────────────────────────────────────────────────────────┤
│ L1  Evidence Store Immutable raw records · SHA-256 · hash chain│
└──────────────────────────────────────────────────────────────┘
```

### 3.2 Components

**L1 — Evidence Store (chain of custody).** Raw log lines are stored immutably with `source_id`, `file`, `line/offset`, `sha256(raw)`, and an ingestion hash chain (`chain_hash = sha256(prev_chain_hash + record_hash)`). Any later tampering breaks the chain, and the report can print the chain head as an integrity anchor. This is cheap to build and reads as "industry-grade" to judges.

**L2 — Parsers and Normalization.** Plugin-style parsers (one class per format) emit a canonical `Event`. Three MVP formats, chosen to differ meaningfully:

1. Auth: JSON lines (IdP style, ISO-8601 with offset)
2. Application audit: key=value or JSON with epoch milliseconds
3. Network: CSV/Zeek-like `conn.log` (epoch seconds, no user, only IPs/hosts)

The normalizer handles timezone and clock-offset annotation, IP canonicalization, hostname case-folding, and event-type mapping onto a small controlled taxonomy (`auth.login.success`, `app.token.create`, `app.data.export`, `net.transfer.outbound`, …).

**Entity resolution.** Identities are linked via explicit, auditable join keys: `user_id`, session ID, token ID, IP, host. Every link records *why* it exists (e.g., `same_user_id`, `host_ip_mapping`). Fuzzy matching is deliberately excluded; low-confidence links are emitted as Inferred, not silently merged.

**L3 — Evidence Graph.**

- Node types: `Event`, `Entity` (user, ip, host, token), `Claim`, `Gap`, `Contradiction`
- Edge types: `OBSERVED_FOLLOWS` (same source ordering), `INFERRED_CAUSAL(rule_id, confidence)`, `SAME_ENTITY(reason)`, `SUPPORTS`, `CONTRADICTS`, `EXPECTED_BUT_MISSING`
- Implementation: NetworkX in-process for the MVP; the schema is portable to Neo4j or Kùzu later.

**L4 — Reasoning Engine (deterministic).**

- *Correlation rules* — declarative YAML plus Python predicates. Each rule has an ID, preconditions, a temporal constraint, an output claim, and a confidence factor list.
- *Confidence model* — additive and explainable: identity match, time proximity, source diversity, expected-sequence match, penalties for clock uncertainty. Output: `{score: 0.74, factors: [{name, delta, why}]}`.
- *Contradiction detector* — impossible ordering, clock-skew inconsistency, identity conflict (same session, two geos in an impossible window), duplicate-but-different records.
- *Expectation (gap) engine* — rules of the form "if A then B should exist within Δt"; a failed expectation creates a `Gap` node.

**L5 — Reporting.** A report builder walks the graph and emits sections: Executive Summary, Reconstructed Timeline, Observed Facts, Inferred Relationships (with rule and confidence rationale), Contradictions, Evidence Gaps, Appendix (raw records and chain head). The optional LLM layer receives *only* the structured claims and may rephrase them. A post-check verifies that every sentence maps back to a claim ID, and anything that does not is dropped.

**L6 — API.** FastAPI endpoints: `POST /cases` (upload logs), `GET /cases/{id}/graph`, `GET /cases/{id}/timeline`, `GET /claims/{id}/provenance`, `GET /cases/{id}/report?format=html|json`, and SSE `/cases/{id}/progress` to drive pipeline animations in the UI.

```json
      {"name": "same_user_id", "delta": 0.35},

    ]
  },
  "limitations": ["No session ID shared between auth and app logs"]
}
```

### 3.4 Example Correlation Rule (declarative)

```yaml
id: R-TOKEN-AFTER-LOGIN
description: API token created by the same account shortly after a successful login
when:
  - event: auth.login.success
  - event: app.token.create
constraints:
  same: [actor.user]
  within_seconds: [0, 600]
  order: first_before_second
emits:
  claim: INFERRED_CAUSAL
  statement: "Token creation follows login for the same account"
confidence:
  base: 0.30
  boosts:
    - {if: "login.network.src_ip not in baseline", delta: 0.15}
    - {if: "gap_seconds < 120", delta: 0.20}
  penalties:
    - {if: "no shared session id", delta: -0.10}
limitations:
  - "Temporal proximity does not prove the login caused the token creation"
expects:
  - event: app.token.use
    within_seconds: [0, 900]
    else: GAP("No audit record of token use")
```

### 3.5 Contradiction and Gap Catalogue

| Type | Detection | Output |
| --- | --- | --- |
| Clock skew | Same host appears in two sources with a consistent offset | Widen `ts_uncertainty_s`, flag ordering as unstable |
| Impossible ordering | Effect timestamp precedes cause beyond tolerance | `Contradiction` node linked to both events |
| Identity conflict | Same token or session used from two unrelated IPs in a short window | `Contradiction` plus a confidence penalty |
| Missing audit | Expected follow-up record absent | `Gap` node |
| Coverage hole | Source has no records for a window where others do | `Gap` (source-coverage) |
| Duplicate divergence | Two records claim the same event with different values | `Contradiction` |

## 4. Demo Cases

Build the synthetic generator so each case ships with **ground truth**; this lets you *measure* the engine rather than just show it.

**Case 1 — The headline: account takeover with an evidence gap.** Login from unfamiliar IP → token created → data export → large outbound transfer → *Unknown: who used the token, what data was read*. This is your main demo story.

**Case 2 — Restraint: a benign look-alike.** Same event types, but the login is from a known corporate IP, MFA passed, and the transfer is a scheduled backup. The engine must **not** escalate. This proves the tool does not overclaim, which is rare and memorable.

**Case 3 — Clock skew.** The app host clock runs 4 minutes behind. The naive timeline puts the token creation *before* the login. TraceWeave detects the offset, widens uncertainty, flags the contradiction, and refuses to assert ordering.

**Case 4 — Identity conflict.** One token used from two IPs in two countries within two minutes. The engine records a contradiction and states both hypotheses (token theft vs a VPN or proxy) without choosing one.

**Case 5 — Missing source.** Network logs have a 7-minute hole during the incident. The engine reports a coverage gap and downgrades confidence in the "no exfiltration" negative conclusion.

**Scoreboard slide for the pitch:** across five cases, report claim-level precision on Observed vs Inferred labelling, gap and contradiction recall, and provenance coverage (100%).

### Expected Output for Case 1

> **Conclusion:** The events are consistent with a possible account-compromise sequence. The logs establish the login, token creation, and outbound transfer. They do **not** independently prove the login caused the transfer, nor do they establish which data was accessed.
>
> **Observed (3):** login 10:02:11 · token created 10:03:04 · outbound transfer 10:05:18 **Inferred (2):** token linked to login (0.74) · transfer linked to token (0.58) **Unknown (2):** token usage · records accessed **Contradictions:** none · **Chain head:** `ab71…`

## 5. UI / UX Direction

Forensic and security tools usually look like spreadsheets. The opening is a **cinematic, editorial investigation tool** that still respects analyst ergonomics. Think of the pattern language of Palantir Gotham, Maltego's graph canvas, Timesketch's timeline, and Linear's polish, wrapped in Awwwards-style motion.

### 5.1 Visual Identity — "The Evidence Room"

- **Mood:** dark, precise, calm; a case file under a desk lamp, not a hacker cliché. Avoid green-on-black matrix styling.
- **Palette:** near-black ink `#0B0D10`, graphite surfaces `#14181D`, paper-white text `#E8E6E1`, and three semantic evidence colors:
  - Observed: warm white or amber `#F2C46D`
  - Inferred: cool cyan `#6FD3E8`
  - Unknown: desaturated violet or hatched grey `#8B7FB8`
  - Contradiction: signal red `#FF5C5C` (used sparingly)
- **Typography:** a distinctive display serif or grotesk for headlines (e.g., Fraunces, Instrument Serif, or Neue Montreal-style), with JetBrains Mono for raw log lines and timestamps. The serif/mono contrast signals "narrative vs evidence".
- **Texture:** subtle film grain, thin 1px rules, and a faint grid. Provenance tags look like evidence-bag labels.
- **Encoding rule (consistent everywhere):** solid = observed, dashed = inferred, hatched = unknown.

### 5.2 Screens

1. **Landing page (the Awwwards moment).** Full-bleed hero where scattered log fragments float as monospace text and are "woven" by animated threads into a single timeline as you scroll. Tagline: *"Know what happened. Know what you can prove."* Sections: the problem (three disconnected logs), the three states, live mini-demo, the five cases, architecture, CTA to open a case.
2. **Case Intake.** Drag-and-drop three files; each file animates into an "evidence bag" card showing format detected, record count, and SHA-256. The hash chain visibly extends.
3. **Pipeline view.** Staged progress (Ingest → Normalize → Correlate → Reason → Report), driven by SSE, with each stage animating counts of events, links, gaps, contradictions.
4. **Investigation workspace (core screen).**
   - *Left:* swimlane timeline (one lane per source plus an "Inferred" lane and a "Gaps" lane).
   - *Center:* evidence graph with solid, dashed, and hatched edges.
   - *Right:* claim inspector showing statement, state badge, rule ID, confidence factor breakdown, limitations, and the **raw record** with line number and hash.
   - *Top:* a time scrubber; scrubbing replays the incident and reveals events in order.
5. **Report view.** Editorial layout of the report with every sentence carrying a small provenance marker that expands to the raw line.
6. **Compare view (cinematic demo).** Side-by-side "naive merged timeline" vs "TraceWeave reconstruction" for Case 3 (clock skew), where the naive version *looks* clean and TraceWeave visibly flags it.

### 5.3 Motion Design with GSAP

Principles: motion must explain (causality, provenance, uncertainty), not decorate; every animation respects `prefers-reduced-motion`; timings 0.4–0.9s with `power3.out` or `expo.out`.

| Moment | Technique |
| --- | --- |
| Hero log fragments converging | `gsap.timeline` with `ScrollTrigger` scrub; fragments tween from random positions to timeline slots |
| Evidence "thread" drawing | SVG paths with `strokeDasharray`/`strokeDashoffset` tween (or DrawSVG if available); dashed style for inferred links |
| Headline reveals | `SplitText` line/char mask reveals on scroll |
| Smooth scroll | Lenis wired to ScrollTrigger |
| Claim card to inspector transition | `Flip` plugin: card morphs into the inspector panel |
| Node hover | Magnetic effect via `quickTo`; neighbors highlight, others fade to 0.25 opacity |
| Pipeline stage counters | `gsap.to` numeric tween with snap |
| Timeline scrubber replay | Master timeline with labels per event; scrub with `timeline.progress()` |
| Contradiction flag | Short red pulse plus a shake with `elastic.out`, once only |
| Hash chain growth | Sequential reveal of chain links with stagger |

```ts
// Draw an edge: solid for observed, dashed for inferred
function drawEdge(path: SVGPathElement, inferred: boolean) {
  const len = path.getTotalLength();
  if (!inferred) {
    gsap.fromTo(path, { strokeDasharray: len, strokeDashoffset: len },
      { strokeDashoffset: 0, duration: 0.8, ease: "power2.out" });
  } else {
    path.style.strokeDasharray = "6 6";
    gsap.fromTo(path, { opacity: 0 }, { opacity: 1, duration: 0.6 });
  }
}
```

### 5.4 UI Stack and Performance Notes

- Next.js (App Router), TypeScript, Tailwind, Zustand for case state.
- Graph: Cytoscape.js with custom node renderers, or React Flow if you prefer DOM nodes that GSAP can target directly.
- Keep animated elements to transform and opacity only; virtualize any list over \~500 events; render the graph on canvas past \~300 nodes.
- Optional WebGL flourish (Three.js or OGL) limited to the landing hero: a subtle particle field of "log fragments".
- Accessibility is non-negotiable and thematically on-brand: keyboard-navigable timeline, ARIA labels on claim states, state never conveyed by colour alone (shape and pattern too), reduced-motion fallbacks.

## 7. Testing Strategy

- **Provenance coverage:** every claim and report sentence resolves to ≥1 record; fail the build otherwise.
- **Determinism:** run twice, diff outputs byte for byte.
- **Ground-truth evaluation:** each generated case ships expected claims, gaps, and contradictions; score precision and recall.
- **Property tests (hypothesis):** shuffling input order never changes the output; adding unrelated noise events never creates new causal claims.
- **No-overclaim test:** nothing derived by rule may be labelled Observed.
- **LLM grounding test (if enabled):** every generated sentence must cite a claim ID; reject otherwise.

## 8. Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| "Plaso already does this" | Position explicitly: TraceWeave consumes events *after* collection and adds provenance and uncertainty; mention Plaso/Timesketch as upstream sources or integrations |
| Rule engine feels toy-like | Show the rule catalogue, confidence factor breakdowns, and ground-truth scoreboard |
| Synthetic data feels contrived | Base formats on real shapes (IdP JSON, Zeek-style conn logs, app audit trails); include noisy benign traffic |
| UI eats the timeline | Build the engine and one clean report first; UI polish begins day 5 |
| LLM hallucination | LLM is optional, post-hoc, and grounded-checked; the default demo runs with it off |
